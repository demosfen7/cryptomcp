# cryptomcp

MCP-сервер рыночного контекста Binance USDⓈ-M Futures для анализа с помощью ИИ.

Реализует модули A1 (data_fetcher) и A2 (metrics) из ТЗ `crypto-scanner-architecture.md`
плюс расширение §12 (фандинг и открытый интерес). Полное описание решений и их
обоснований — в [PLAN.md](PLAN.md).

**Принцип: агрегаты считает код, структуру читает модель.** Индикаторы,
перцентили и сезонные поправки — детерминированный Python, покрытый тестами.
Интерпретация формы — работа модели, которой отдаются сырые свечи.

---

## Что он делает

Три уровня выдачи. Модель идёт сверху вниз и останавливается, как только хватит.
Каждый инструмент работает по обоим рынкам Binance: `market="futures"`
(перпетуал, по умолчанию) и `market="spot"`.

| Инструмент | Уровень | Назначение |
|---|---|---|
| `get_market_snapshot` | L1 | Общая картина: лестница таймфреймов, уровни, пивоты, деривативы, индекс |
| `get_squeeze_metrics` | L2 | Пять групп признаков ТЗ §4.2, каждое число с базой сравнения |
| `get_klines` | L3 | Сырые закрытые свечи (≤50) — когда важна форма, а не агрегат |
| `get_key_levels` | — | Кластеры S/R, недельные и дневные пивоты, POC и Value Area |
| `get_derivatives` | — | Фандинг в годовых с историей ставок, открытый интерес: дельты, почасовой ряд с ценой, классификация «цена × OI» |
| `scan_pairs` | — | Пакетное сканирование по squeeze_index |
| `list_symbols` | — | Отбор торгуемых пар по обороту |

Спот нужен, когда перпетуал тонкий: подтверждение пробоя объёмом честнее
искать там, где происходит поставка. Деривативов у спота нет, а списки символов
у рынков не совпадают в обе стороны — часть монет есть только на одном.

## Сборщик данных

Рядом с сервером работает второй контейнер — `cryptomcp-collector`. Он ничего
не отвечает, только копит то, что нельзя восстановить: раздел `/futures/data/`
у Binance отдаёт открытый интерес, соотношения long/short и долю
тейкер-покупок лишь за последние 30 суток. Час без записи — час, потерянный
навсегда; свечи и фандинг, наоборот, докачиваются за годы в любой момент.

```bash
python -m cryptomcp.collector backfill   # забрать доступные 30 суток
python -m cryptomcp.collector once       # один проход дозаписи
python -m cryptomcp.collector loop       # то же раз в час (режим контейнера)
python -m cryptomcp.collector watch      # список наблюдения
python -m cryptomcp.collector add CAKEUSDT --tf 4h   # добавить вручную
```

Список наблюдения набирается **рангом, а не порогом**: вход в топ-15 по
индексу внутри своего таймфрейма, выход из топ-40. Порог сейчас взять неоткуда
— исходы ещё не накоплены, а измеренное распределение не даёт естественной
границы: выше 0.5 не проходит никто, выше 0.3 проходит треть рынка. Ранг
самонормируется и заменится на измеренный порог, когда накопится статистика.
Ручные записи по рангу не выбывают.

Заодно он ведёт архив свечей: 1w и 1d за пять лет, 4h за три года, 1h за два.
Источник — спот там, где спотовая пара есть, и фьючерс для тех четверти
перпетуалов, у которых её нет; выбранный источник закрепляется за символом,
чтобы в одном ряду не склеились два рынка. 15m и мельче не хранятся: год
пятнадцатиминуток весит больше всей остальной лестницы, а докачать их можно
за один проход в любой момент.

Каждый час он же считает индекс по всему архиву и пишет в `scan_log` — по
строке на закрытую свечу, со всеми компонентами по отдельности. Это не стоит
ни одного запроса к бирже: свечи уже в базе. Когда горизонт записи истекает
(24ч, 72ч, 7 суток), в `outcomes` ложится, что за это время произошло с ценой —
по High/Low внутри периода, а не по закрытию, иначе достигнутые и откатившиеся
цели не засчитываются.

Данные ложатся в SQLite (`CRYPTOMCP_DB`, в контейнере — именованный том).
Пишет в базу только сборщик; MCP-сервер будет её читать.

## Чего он не делает

Не предсказывает направление, не даёт торговых рекомендаций и не умеет
торговать. В проекте нет ни одного API-ключа, а все торговые эндпоинты Binance
требуют подписи — торговые операции невозможны конструктивно, а не по
договорённости.

`squeeze_index` измеряет готовность к движению, а не его сторону. Это эвристика
с неоткалиброванными весами; её прогностическая ценность неизвестна, пока не
накопится статистика.

## Установка

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev]"
```

Требуется Python 3.12+. Разрабатывается и разворачивается на 3.14 — pandas 3.0
и numpy 2.5 ставятся туда колёсами без сборки, поэтому расходиться версиями
между разработкой и продом незачем.

На Windows консоль по умолчанию cp1252, и вывод с кириллицей падает с
`UnicodeEncodeError`. Перед запуском скриптов:

```bash
export PYTHONIOENCODING=utf-8
```

## Проверка

```bash
pytest -q && ruff check cryptomcp/ tests/
```

Тесты не ходят в сеть: всё считается на синтетических рядах с известным
ответом, поэтому прогон не зависит от доступности биржи и не расходует лимит.

## Локальный запуск (stdio)

```bash
python -m cryptomcp.server
```

Регистрация в Claude Code:

```bash
claude mcp add cryptomcp -- /полный/путь/.venv/Scripts/python -m cryptomcp.server
```

## Удалённый запуск (HTTP)

```bash
MCP_AUTH_TOKEN=$(openssl rand -hex 32) CRYPTOMCP_TRANSPORT=streamable-http python -m cryptomcp.server
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CRYPTOMCP_TRANSPORT` | `stdio` | `stdio` или `streamable-http` |
| `CRYPTOMCP_PORT` | `8000` | Порт HTTP-режима |
| `CRYPTOMCP_PUBLIC_HOST` | `0.0.0.0` | Домен за прокси (проверка заголовка Host) |
| `MCP_AUTH_TOKEN` | — | Токен доступа. Без него сервер отвечает без аутентификации |
| `CRYPTOMCP_CONFIG` | — | Путь к YAML с порогами, см. `config.example.yaml` |
| `CRYPTOMCP_LOG_LEVEL` | `INFO` | Уровень лога (всегда в stderr) |

`/health` открыт без токена, `/mcp` требует токен.

## Подключение

Боевой сервер: **https://cryptomcp.aithinglab.com/mcp**

Токен принимается двумя способами. Приоритетный — `Authorization: Bearer <токен>`.
Запасной — `x-api-key: <токен>`, одним значением, без префикса.

Второй нужен для custom connector на claude.ai: там имя `Authorization`
зарезервировано под OAuth и вручную не задаётся.

| Способ | Как настроить |
|---|---|
| Коннектор claude.ai | URL сервера, Header-Name `x-api-key`, значение — токен. Работает во всех чатах, в вебе и на телефоне |
| Claude Code, этот проект | `.mcp.json` в корне (в git не попадает, содержит токен) |
| Claude Code, глобально | `claude mcp add --transport http cryptomcp <URL> --header "Authorization: Bearer <токен>"` |
| Локально без сервера | `python -m cryptomcp.server` — транспорт stdio, токен не нужен |

Токен лежит в `.env` рядом с проектом и в секретах GitHub (`MCP_AUTH_TOKEN`).
Смена: сгенерировать новый, `gh secret set MCP_AUTH_TOKEN`, запустить деплой,
обновить значение в коннекторе и в `.mcp.json`.

OAuth не реализован. Для одного пользователя статического токена достаточно;
если понадобится, SDK его поддерживает — нужны эндпоинты authorize, token и
динамической регистрации плюс хранилище кодов.

## Решения, которые легко нарушить по неосторожности

Каждое сопровождается тестом; ниже — зачем они нужны.

**Незакрытая свеча отсекается на входе, в `series.py`.** Её объём и диапазон
неполные, поэтому любая метрика поверх смещена. Отсечение сделано так, что ни
один индикатор физически не может её увидеть. Закрытость определяется по часам
биржи (расхождение с локальными измерялось в 1.5 секунды) с запасом в 5 секунд.

**Ни одно число не печатается без базы сравнения.** Перцентиль требует и ≥60
наблюдений, и ≥60 суток охвата; иначе печатается причина, а не значение.
Единственное исключение — открытый интерес: биржа хранит его историю только
30 суток, и оговорка едет вместе со значением.

**Объём считается в котируемой валюте (USDT), не в базовой.** Иначе на паре,
выросшей втрое, объём «падает» просто потому, что за те же деньги покупают
меньше монет.

**Объём сравнивается с сезонной базой.** У крипты сильная суточная сезонность,
и плоская MA20 показывала бы «затухание» там, где просто ночь. При этом форма
суток берётся с длинного окна, а уровень — со свежего: наивная медиана слота за
60 суток смешивает сезонность с дрейфом активности и завышает показания вдвое.

**База объёма одна на всю выдачу — `volume.baseline_series`.** Снапшот берёт её
последнее значение, `get_klines` — весь показанный хвост. Второй нормировки
быть не должно: пока в `get_klines` стояло среднее по показанному окну, одна и
та же свеча получала разные числа в двух похоже названных колонках, а внутри
`get_klines` — ещё и разные при разном `limit`. Поэтому ряд для L3 берётся на
500 свечей независимо от `limit`.

**«Длительность» диапазона — это длительность сжатия.** `narrow_bars` считает
свечи подряд, у которых ширина диапазона(20) ниже порога ТФ. У широкого
диапазона там ноль — верное значение, а не сбой счётчика. Подписывать это
словом «держится» рядом с границами диапазона нельзя: читается как возраст
диапазона.

**У каждого числа видно, к какому моменту оно относится.** Снапшот печатает
границу закрытия по каждому ТФ отдельно, `get_key_levels` подписывает, что его
цена — закрытие свечи, а не live. Иначе расхождение между инструментами
(1.8440 против 1.8375 на CAKE) читается как ошибка одного из них.

**Динамика OI считается по числу контрактов, не по стоимости.** При росте цены
на 5% стоимость OI вырастет на те же 5%, даже если ни одна позиция не открылась.

**Группа без достаточной базы исключается из индекса, а не обнуляется**, веса
оставшихся перенормируются. Ноль означал бы «признака нет», хотя его не удалось
измерить.

**Рынок пишется в журнал.** Иначе спотовые и фьючерсные записи по одному
символу смешаются, и калибровка весов пойдёт по мешанине из двух разных
инструментов: `formula_version` их не различает.

**У рынков раздельные пулы веса и разный потолок страницы** (1500 свечей у
фьючерсов, 1000 у спота — на `limit=1500` спот молча возвращает 1000). Поэтому
клиент на каждый рынок свой, а пагинация считает страницы по потолку рынка.

**Составной инструмент возвращает частичный результат, а не отказ.** Нехватка
истории на одном таймфрейме не отменяет остальные: строка помечается причиной,
данные по прочим ТФ считаются. Целиком ошибка остаётся, только если не посчитан
ни один таймфрейм. Свежие листинги — целевая категория сканера, и падать именно
на них нельзя.

**Узость диапазона меряется перцентилем по истории самой монеты, а не
абсолютным порогом.** Абсолютный порог из ТЗ (6–8% по таймфреймам) на живом
рынке не срабатывал ни у кого: медианный дневной диапазон 65%. Четверть веса
формулы простаивала. Единый порог для BTC и для свежего листинга бессмыслен так
же, как единый множитель объёма.

**При изменении весов или формулы поднимать `SQUEEZE_FORMULA_VERSION`.** Без этого записи
журнала до и после калибровки станут несопоставимы, и накопленное пропадёт.

## Как проверять изменения

Зелёных тестов недостаточно. Четыре ошибки в этом проекте нашлись не тестами, а
живыми данными, и все четыре — в модулях со стопроцентно зелёной синтетикой:
сцепление в кластеризации уровней, смешение сезонности с дрейфом активности в
объёмной базе, молчание классификации OI при накоплении и неразличение знака OI
в ней же. Синтетика их не ловила, потому что в неё закладываешь то, что уже
понял.

Поэтому после правки любого расчётного модуля — прогон на реальном символе с
просмотром выдачи глазами. BTCUSDT и SUIUSDT дают разный масштаб цены и
волатильности и вместе вскрывают большинство ошибок нормировки.

Локально тесты запускать так же, как их запускает CI — командой `pytest`, а не
`python -m pytest`. Разница не косметическая: `python -m` кладёт текущую папку в
`sys.path`, и импорт, который на runner'е падает, локально проходит. Ровно на
этом CI поймал кросс-импорт между тест-модулями, зелёный у себя.

Сверять CI-забег нужно по SHA коммита, а не брать последний в списке: сразу
после push там может стоять забег предыдущего коммита.
