# ТЗ: стакан ликвидности (L2 order book)

Версия 1. Основание — запрос на `get_order_book` / `track_order_book`,
разбор архитектурного несоответствия текущей модели сборщик/сервер.
Кода не требуется, только поведение и границы.

---

## 0. Почему документ разбит на две части

Запрос смешивает два инструмента разной весовой категории:

| | Часть A | Часть B |
|---|---|---|
| Источник | REST snapshot | WS diff-depth, непрерывно |
| Состояние | нет, каждый вызов независим | есть, требует реконструкции и хранения |
| Куда встраивается | сервер, по образцу существующих инструментов | новый процесс, не сборщик и не сервер |
| Готовность к реализации | сейчас | после того как часть A отработает и появится поток сделок для сверки |

**Часть B не начинать, пока не выполнены три предусловия** (раздел B.0).
Собирать их в одну задачу для программиста — способ получить нерабочий
детектор спуфинга поверх рабочего REST-инструмента, и вторым будет
незаметно испорчен первый.

# Часть A. `get_order_book`

## A.1. Зачем

Текущие инструменты (`get_klines`, `get_derivatives`, `get_squeeze_metrics`)
показывают, что уже произошло со свечой. Ни один не показывает, чем именно
подкреплён текущий уровень — толстым лимитным стаканом или тонким воздухом
в один тик. `get_order_book` закрывает это для одного момента времени.
Не путать с вопросом «что происходит с заявками во времени» — это часть B.

## A.2. Параметры

| Параметр | Тип | Обязателен | Примечание |
|---|---|---|---|
| `symbol` | string | да | как в остальных инструментах |
| `market` | `spot` \| `futures` | нет, по умолчанию `futures` | как в остальных инструментах |
| `limit` | int | нет, по умолчанию `100` | **строго enum Binance: 5, 10, 20, 50, 100, 500, 1000, 5000.** Значение не из списка — ошибка валидации, а не округление |
| `depth_pct` | float или список float | нет | диапазон(ы) в процентах от `last_price`, например `[0.25, 0.5, 1, 2, 5]` |

**`as_of_ms` не предусмотрен.** В отличие от свечей, у биржи нет архива
состояний стакана — REST отдаёт только «сейчас». Ретроспектива по стакану
существует только там, где часть B её накопила, и это отдельный параметр
отдельного инструмента, не флаг этого.

### A.2.1. `depth_pct` не гарантирует покрытие диапазона

`limit` определяет количество уровней, `depth_pct` — что из полученных
уровней показывать. Если на выбранном `limit` фактическая глубина не
доходит до заявленного `depth_pct` (тонкий стакан, широкий процент),
инструмент обязан сказать это явно, а не тихо обрезать диапазон:

```
depth_pct 5% запрошен, фактическое покрытие 3.1% при limit=1000 —
дальше стакана нет ни на одной стороне
```

Наращивать `limit` до максимума автоматически, чтобы дотянуть до
`depth_pct`, — не входит в задачу без явного флага `auto_expand`,
потому что это меняет вес запроса на порядок без предупреждения.

## A.3. Стоимость запроса — Binance API weight

| `limit` | weight |
|---|---|
| 5–100 | 5 |
| 500 | 25 |
| 1000 | 50 |
| 5000 | 250 |

Печатать в ответе, каким `limit` фактически обслужен запрос, и не
подтягивать `limit=5000` по умолчанию ради надёжного покрытия
`depth_pct` — это будет стоить 50x по весу против `limit=100` при
каждом вызове. Значение по умолчанию — компромисс, не гарантия.

## A.4. Сырые данные — обязательный блок

```
timestamp          момент снапшота, мс
last_price
best_bid / best_ask
spread             best_ask − best_bid
spread_pct         spread / last_price × 100

bids: [{ price, qty, notional_usdt, cum_notional_usdt }, ...]
asks: [{ price, qty, notional_usdt, cum_notional_usdt }, ...]
```

`cum_notional_usdt` — накопительная сумма от лучшей цены до данного
уровня, входит в сырой блок, а не только в агрегаты: без неё нельзя
проверить агрегаты вручную по сырым уровням, а это правило проекта
для любой производной величины.

## A.5. Агрегаты — отдельным блоком, не смешивать с сырыми

### A.5.1. Notional и imbalance по диапазонам

Для каждого из `depth_pct` (по умолчанию 0.25 / 0.5 / 1 / 2 / 5%):

```
bid_notional_usdt
ask_notional_usdt
imbalance = (bid_notional − ask_notional) / (bid_notional + ask_notional)
```

`imbalance` в диапазоне [-1, 1]. Печатать `n/a` с причиной, если оборот
монеты ниже 2M USDT/сутки (порог из остальной методики проекта, единый
для всей системы) — на тонком рынке несколько крупных заявок дают
имбаланс, не отражающий ничего устойчивого.

### A.5.2. Крупные уровни («стены»)

**База сравнения — не медиана текущего снапшота.** Это отдельно
проговаривается, потому что база объёма в этом проекте уже расходилась
четыре раза между сканером/метриками, 1d/4h, графиком/архивом — всегда
по одной причине: сравнение с не той выборкой. Здесь база — **собственное
распределение размеров уровней этого символа за скользящее окно** (не
меньше нескольких сотен снапшотов), а не среднее по видимым сейчас 100
уровням одного стакана. Средний размер уровня в одном снапшоте — не
статистика, это одна точка.

Пока такой истории нет (см. часть B), инструмент обязан отвечать `n/a` с
причиной «нет базы», а не считать относительно текущего снапшота —
ровно то правило, что уже действует для перцентилей волатильности.

Для каждой стены печатать:
```
price
qty / notional_usdt
distance_pct        расстояние от last_price, %
ratio_to_baseline   размер / медиана собственной истории (или n/a)
side                bid / ask
```

### A.5.3. Кластеры соседних крупных заявок

Определение по аналогии с схлопыванием баров в детекторе распределения:
**N соседних ценовых уровней, каждый ≥ X от базовой линии, объединяются
в один кластер**, а не считаются N отдельными стенами. Порог `X` и `N` —
стартовые и не откалиброванные величины, обязательна секция калибровки
(A.11), как во всех остальных ТЗ проекта. Не подбирать порог сейчас на
глаз — сначала накопить наблюдения.

## A.6. Что инструмент НЕ делает

- не хранит историю — каждый вызов независим от предыдущего;
- не оценивает намерение (спуфинг, манипуляция) — это вопрос части B,
  и то с оговорками из раздела B.7;
- не различает одного участника с крупной заявкой от суммы множества
  мелких на одном уровне — Binance не отдаёт число ордеров на уровне,
  только суммарный объём;
- не учитывает айсберг-ордера: видимый размер уровня — не факт полного
  размера заявки. Печатать это ограничение в описании инструмента, а не
  только в этом документе, чтобы модель, вызывающая инструмент, не
  делала более сильных выводов, чем данные позволяют.

## A.7. Частичный результат вместо отказа

Действует общее правило проекта (ARCHITECTURE §7): нехватка данных на
одном участке не должна обрушивать весь ответ. Если `depth_pct` не
покрыт целиком — печатать то, что есть, плюс явную причину (A.2.1). Если
база для стен ещё не набралась (A.5.2) — агрегаты по notional печатаются,
блок стен помечается `n/a`, ответ не проваливается целиком.

## A.8. Формат выдачи (пример структуры, не реальные данные)

```
Стакан ARBUSDT.P, снапшот 2026-09-16 14:03:11 UTC
last_price 0.4521 · best_bid 0.4520 · best_ask 0.4522 · spread 0.04%

Диапазон ±0.25%   bid 812K · ask 640K · imbalance +0.12
Диапазон ±0.5%    bid 1.44M · ask 1.30M · imbalance +0.05
Диапазон ±1%      bid 2.9M · ask 3.1M · imbalance −0.03
Диапазон ±2%      bid 5.1M · ask 6.0M · imbalance −0.08
Диапазон ±5%      покрытие неполное: фактически ±3.1% при limit=1000

Крупные уровни (база: n/a — истории размеров уровней пока нет)
  0.4510 bid  340K  −0.24%
  0.4535 ask  290K  +0.31%

Кластеры: не рассчитаны (нужна база из A.5.2)
```

## A.9. Приёмочные тесты

| # | вход | ожидание |
|---|---|---|
| 1 | `limit=30` (не из enum) | ошибка валидации, а не тихое округление до 20 или 50 |
| 2 | `depth_pct=5` на монете с тонким стаканом при `limit=100` | ответ содержит фактическое покрытие и причину, не тихо урезанный диапазон |
| 3 | сверка баз | `cum_notional_usdt` последнего уровня диапазона обязан совпадать с суммой `notional_usdt` всех уровней внутри этого диапазона, посчитанной вручную по сырому блоку |
| 4 | монета с оборотом < 2M USDT/сутки | `imbalance` = `n/a` с причиной, сырые bids/asks печатаются как есть |
| 5 | запрос без истории размеров уровней (до реализации части B) | блок стен и кластеров = `n/a` с причиной «нет базы», а не расчёт от снапшота |
| 6 | `market=spot` и `market=futures` на одном символе в один момент | два независимых ответа, никакого смешения книг |

## A.10. Калибровка

Пороги стены и кластера (A.5.2, A.5.3), а также ширина окна для базовой
линии — **стартовые и не откалиброваны**. Взять их можно будет только
после того, как часть B начнёт копить историю размеров уровней по
символам; до этого любое число — угадывание, как и везде в проекте.

# Часть B. `track_order_book` — контракт на будущее

## B.0. Предусловия — не начинать без них

1. Часть A в проде минимум несколько недель, база размеров уровней
   (A.5.2) реально накопилась хотя бы для нескольких символов.
2. Есть оценка объёма хранения по факту, а не на бумаге — см. B.4.
   Существующий проект всегда считает стоимость до реализации
   (пример — решение по глубине деривативов в ARCHITECTURE §2); здесь
   такого замера сделать заранее нельзя, потому что неизвестна частота
   изменений стакана без пилота.
3. Добавлен поток исполненных сделок (`aggTrade`) для той же пары.
   Без него часть B физически не может отличить «заявка исполнилась»
   от «заявка снята» — это не техническая деталь, а причина, по которой
   весь раздел B.6 без него не работает.

## B.1. Зачем

Один снапшот не отличает реальную ликвидность от временной. Нужна
последовательность: появилась ли крупная заявка, растёт или уменьшается,
двигается ли за ценой, исчезла ли перед касанием, была ли исполнена,
сколько простояла.

## B.2. Почему это не сборщик и не сервер

| | сервер | сборщик | процесс части B |
|---|---|---|---|
| Режим | отвечает по запросу | раз в час | непрерывный WS-слушатель |
| Отказ на час | никто не пострадал | потерян час OI навсегда | потерян интервал стакана навсегда, и хуже — неизвестно, потерян ли он полностью или частично (пропущенное событие в середине потока не всегда заметно без проверки последовательности) |
| Восстановимость после сбоя | не нужна | не нужна | REST-снапшот восстанавливает точку, но не историю переходов между ней и предыдущим состоянием |

Нужен третий режим отказа, а не переиспользование готовых двух. Это
отдельный контейнер со своим healthcheck: «жив ли WS-коннект и когда
был последний успешный ресинк», а не «был ли прогон за последние два
интервала» — метрика сборщика сюда не подходит.

## B.3. Реконструкция стакана — обязательная процедура, не деталь реализации

Стандартный алгоритм Binance, и он должен быть прописан явно, потому что
это единственное место в системе, где ошибка не считается быстро и не
падает с исключением — она тихо накапливается:

1. Открыть WS `<symbol>@depth`, начать буферизовать события.
2. Запросить REST snapshot, получить `lastUpdateId`.
3. Отбросить все забуференные события с `u <= lastUpdateId`.
4. Первое применяемое событие должно удовлетворять
   `U <= lastUpdateId + 1 <= u`. Если такого нет среди буфера — снапшот
   устарел, запросить заново.
5. Каждое следующее событие проверяется на непрерывность с предыдущим
   (`pu` нового события должно равняться `u` предыдущего для futures).
   Разрыв — не ошибка соединения, а сигнал немедленного полного ресинка,
   и текущее состояние стакана до ресинка помечается недостоверным, а
   не отдаётся как достоверное.

**Тест на этот раздел обязателен до тестов на бизнес-логику**: без него
любая метрика поверх реконструированного стакана недостоверна тем же
способом, каким уже был недостоверен счётчик `узк` при двух разных
вычислителях перцентиля (knowledge-base §5, П1) — только здесь ошибка
не в формуле, а в самих входных данных.

## B.4. Хранение — не полный стакан на каждое обновление

Полный снимок стакана на каждое WS-событие — сотни мегабайт в день на
один тонкий символ, для всего watchlist это неприемлемо без оценки.
Хранить не состояние, а **события уровня** — по аналогии с тем, что
детектор распределения хранит события, а не бары:

```
level_events: symbol, side, price, qty_before, qty_after,
              event_type (appeared / grew / shrank / disappeared),
              ts, ts_since_appeared
```

Полный снапшот сохранять не при каждом изменении, а по расписанию
(например раз в N секунд) для возможности восстановления и сверки —
периодичность и N определить после пилота, не сейчас.

## B.5. Определение «крупной заявки»

Та же база, что уже введена в A.5.2 — собственная историческая
распределение размеров уровней символа, не абсолютное число и не медиана
одного снапшота. Заводить вторую, отдельную базу для части B значит
повторить болезнь из knowledge-base §3 внутри одного инструмента.

## B.6. Состояния уровня — только при выполнении B.0.3

| состояние | критерий | требует потока сделок |
|---|---|---|
| `appeared` | новый уровень ≥ порога, не существовавший в предыдущем снапшоте | нет |
| `growing` / `shrinking` | изменение `qty` ≥ X% между снапшотами | нет |
| `moved_with_price` | уровень сдвигается вместе с mid-price, дистанция в % остаётся стабильной | нет |
| `filled` | уровень исчез, и за тот же интервал поток сделок показывает исполнение сопоставимого объёма по этой цене | **да** |
| `disappeared` | уровень исчез, поток сделок НЕ показывает исполнения — заявка снята | **да** |

Без потока сделок последние два состояния неразличимы принципиально —
это переформулировка из B.0.3, повторена здесь, потому что именно тут
он чаще всего будет пропущен при реализации по частям.

## B.7. Чего детектор не может сказать

- не доказывает намерение (спуфинг как манипуляция — юридический и
  поведенческий вывод), только фиксирует паттерн: заявка появилась и
  исчезла без исполнения перед касанием ценой;
- не отличает одного участника от множества независимых, если они
  случайно оказались в одном событии `disappeared`;
- айсберг-ордера дают ложный `disappeared` при каждом обновлении
  видимого объёма — без признака «немедленно появился похожий уровень
  на той же цене» это будет систематическая ложная тревога, а не
  случайная. Признак обязателен в реализации, не факультативен.

## B.8. Ложные срабатывания

- **Тонкий рынок.** Порог 2M USDT/сутки из основной методики действует
  и здесь: ниже него `n/a` с причиной, не `disappeared`.
- **Рутинное перевыставление маркет-мейкером.** Отмена и мгновенная
  повторная постановка на соседнем тике — не «исчезновение», это шум
  котирования. Нужен временной зазор допуска (сколько мс/тиков считать
  «тем же уровнем») — величина для калибровки, не для угадывания сейчас.

## B.9. Формат выдачи (структура, не реальные данные)

```
Событие: крупная заявка ARBUSDT.P bid 0.4510
  появилась       2026-09-16 13:40:02 UTC, notional 340K (× 4.1 к базе)
  движение        держалась на дистанции 0.20-0.24% от цены 3 минуты
  исход           disappeared 13:44:51, поток сделок за интервал: исполнено 12K
                   из 340K — вывод: заявка снята, не исполнена
  длительность    4м49с
```

## B.10. Приёмочные тесты

Конкретные тесты на реальных символах/датах появятся только после
пилота части B — до того, как накопится история, тестовых случаев с
реальными числами быть не может, и вписывать их сейчас значило бы
имитировать эмпирику, которой нет. Обязательный протокол для получения
тестов:

1. запустить на 3–5 символах минимум на неделю;
2. вручную сверить 10–20 событий `filled`/`disappeared` по графику и
   ленте сделок биржи;
3. только после совпадения фиксировать пороги B.6/B.8 числами и писать
   тесты по образцу остальных ТЗ проекта.

## B.11. Калибровка

Все числовые пороги этой части (X% в B.6, зазор допуска в B.8, окно
базовой линии) — не определены сейчас намеренно. Опыт проекта с
`squeeze_index` и детектором распределения показывает, что число,
взятое без пилота, придётся менять, и лучше не закладывать его в схему
до того, как появится статистика.
